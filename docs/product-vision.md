# SignalFeed 产品愿景与路线图

> 文档状态：生效中  
> 最近更新：2026-08-14

## 1. 产品定位

SignalFeed 是一个面向大模型与 AI 开发领域的高信噪比信息采集工具。它从高价值官方站点和开发者社区持续发现新内容，经过标准化、过滤和去重后，以简报形式推送到飞书。

项目要解决的核心问题是：AI 开发信息分散、更新频繁、重复内容多，开发者需要花费大量时间浏览多个网站和社区，才能找到真正值得阅读的信息。

SignalFeed 的核心目标是：

> 让使用者每天自动获得一批值得阅读的大模型与 AI 开发信息，而不必手动巡检多个来源。

## 2. 产品原则

- **信噪比优先**：来源数量不是成功指标，稳定输出有阅读价值的内容才是。
- **官方来源优先**：同一事件优先保留厂商官网、项目 Release 等原始来源。
- **确定性优先**：早期使用可理解、可配置、可测试的过滤和去重规则。
- **闭环优先**：先确保采集、筛选、去重、推送能够持续运行，再扩充来源。
- **小步演进**：不为尚未验证的需求提前引入复杂基础设施。

## 3. 目标信息范围

重点关注以下内容：

- 模型、API、SDK 和开发者工具发布或更新；
- Agent、AI Coding、MCP、推理框架等工程进展；
- 重要开源项目、模型和开发工具；
- 有实际参考价值的开发者使用经验；
- 与上下文、推理、评测和部署相关的重要变化。

论文流、泛科技资讯和缺少事实信息的营销内容不是当前重点。

## 4. 路线图

### 单一官方信源闭环

该闭环验证从真实官方信源到飞书消息的端到端技术路径：

```text
OpenAI 官方 RSS
        ↓
      采集
        ↓
 NewsItem 标准化
        ↓
    关键词过滤
        ↓
   SQLite 去重
        ↓
 飞书消息 / 安全预览
```

上述单一官方信源闭环已经完成工程实现和真实飞书发送验收。具体设计和状态见 [单一官方信源闭环技术规格](single-source-specification.md)。

### 中文简报与真实联网验收

在扩充信源前，先把单一官方信源闭环的英文 RSS 摘要升级为可直接阅读的中文简报：

```text
OpenAI 官方 RSS → 英文关键词过滤 → 送达去重
        → Jina 正文提取 → Responses 模型中文化
        → 中文缓存 → 飞书消息 → 成功后记录送达
```

每篇内容生成一个简体中文标题和 3–5 条完整中文要点，并保留产品名、模型名、数字和限定条件。正文作为不可信数据处理，不使用英文回退；成功生成的结果会缓存以便下轮复用。模型请求可以并行执行，输出顺序保持确定。该阶段验证了单信源中的正文提取、摘要缓存、北京时间和飞书大小边界；多信源阶段进一步把失败隔离和送达记账收缩到单篇文章。

当前代码、自动化测试及 OpenAI RSS → Jina → 模型 API 的真实 dry-run 已通过；当前 20 条窗口已分两批真实发送，最终重复运行输出 `No new matching items.`。中文简报与真实联网验收完成。

### 自动部署与定时调度：已实现，7 天观察中

`main` 的 CI 成功后会通过 SSH 部署同一个已验证 commit；部署前再次确认远端 `main`，并与 systemd 任务共用文件锁，避免旧 workflow 回滚或在运行中更新环境。一次性 CLI 由 systemd timer 在北京时间每天 `08:30`、`12:30`、`21:00` 调用，错过计划后恢复时补跑一次；早间档在 DeepSeek 09:00 起的峰段定价开始前完成模型调用。

自动部署、定时调度、互斥和运行超时已经完成工程实现。当前状态仅标记为“7 天观察中”，尚未标记运行验收完成；需连续观察 21 个计划时点均成功发送或正常输出 `No new matching items.`，且无重叠运行、异常重复推送和人工修复后再完成验收。

### 六厂商多信源扩展：实现与验收中

当前迭代已把模型厂商官网作为第一批稳定信源，覆盖 OpenAI、Anthropic、DeepSeek、Kimi、GLM 和 MiniMax 的 News、Developer Blog、Engineering/Research、模型发布和 API/平台更新，共 14 个官方入口。

```text
有序 [[sources]]
      ↓
五种确定性 Collector → CollectionBatch(items, issues)
      ↓
原精度日期、全局关键词（按源启用）、规范化 URL/内容签名去重
      ↓
新来源基线 ── 已初始化来源的新条目
                         ↓
       单篇正文 → 单篇中文摘要 → 单篇飞书消息 → 立即记账
                         ↓
       局部失败继续后续文章，并对同一故障只告警一次
```

配置顺序决定跨来源相同 URL 的优先级；Changelog 通过来源、日期和内容签名区分同页多条记录。首次见到的新来源只建立窗口基线，不补发历史内容。摘要仍可并行，但消息按来源与官方列表顺序逐篇发送，每篇恰好一条。

来源或文章失败不再中止整轮。已成功摘要和已成功发送的文章分别立即缓存和记账；小型飞书告警通过 SQLite 活动故障状态避免重复提醒，并在来源恢复或文章送达后静默清除。完整设计、信源目录和验收矩阵见[六厂商多信源技术规格](multi-source-specification.md)。

这一阶段不包含标题相似度、语义去重、评分排序，也不把 Kimi 页面发现的 GitHub/Hugging Face 项目链接扩展为主动信源。完成全部自动化检查和 14 个真实入口联网 dry-run 后进入连续运行观察。

### 后续路线：社区与项目来源

六厂商官方入口稳定后，再根据实际内容缺口评估：

1. GitHub 指定组织的新仓库和指定仓库 Release；
2. Hugging Face 新模型、Trending Models、Trending Spaces 和指定厂商账号；
3. Hacker News 中高价值的 AI 开发者实践与真实使用反馈。

这些来源必须复用现有的标准化、基线、精确去重、中文摘要、失败隔离和告警边界。是否需要排序评分或更强去重，应由真实重复率决定。

### 后续评估：补充高成本渠道

第一阶段稳定后，再评估接入：

- X / Twitter；
- 知乎。

这两个渠道属于后续评估目标，但不阻塞扩充稳定信源阶段上线。是否接入 V2EX、Reddit 等社区，应由实际内容缺口决定。

## 5. 多信源稳定标准

满足以下条件后，扩充稳定信源阶段可视为稳定：

1. 14 个厂商官方入口能够持续采集并统一转换为领域模型；
2. 新来源只建立基线，不补发历史内容；
3. 跨来源重复 URL 不会反复推送，Changelog 同页多条不会互相覆盖；
4. 关键词规则能筛选一般新闻，策展技术入口不会被误过滤；
5. 单篇故障不阻塞其他内容，同一故障只告警一次且恢复后可再次提醒；
6. 飞书按官方顺序逐篇发送结构清晰的中文内容；
7. 系统连续运行一周，无需日常人工干预；
8. 大多数推送内容对目标使用者具有实际阅读价值。

## 6. 当前非目标

当前非目标包括：

- Web 前端、RSS 阅读器或用户账户；
- 个性化推荐、Embedding、向量数据库或 LLM 内容评分；
- 论文摘要和论文推荐；
- Codex、Claude Code、Kimi Code、MiniMax Agent 的逐版本补丁流水；
- 标题相似度或 LLM 语义去重；
- GitHub/Hugging Face 主动发现；
- Redis、PostgreSQL、Elasticsearch 或 GPU 基础设施；
- 微信公众号、ModelScope、小红书、微博、B 站等扩展渠道。

上述能力只有在现有闭环稳定且出现明确需求时才重新评估。
